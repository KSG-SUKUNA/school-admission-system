# Assumptions and design decisions

The assignment leaves some implementation details open. The following decisions are used consistently by the backend, database, and UI.

1. **A class/shift is one admission unit.** `Class 6 - Morning Shift` and `Class 6 - Day Shift` are separate records with independent seat capacities, as required by the UI/API description.
2. **Student identity is a 17-digit birth-registration number.** The UI stores it in browser local storage and sends it in the `X-Student-Id` header. No login or authentication is added because the assignment explicitly says login is not required. This is a take-home demonstration, not a production identity-verification mechanism.
3. **One active or confirmed application per student per class.** `HELD` and `CONFIRMED` both prevent another application for the same student/class. `EXPIRED` and `CANCELLED` records do not prevent a later application.
4. **Hold duration defaults to 600 seconds.** `HOLD_DURATION_SECONDS` overrides it. The backend clamps the configured value to 1–86,400 seconds to prevent invalid or unbounded values. Timestamps are stored and compared in UTC.
5. **Expired holds are released automatically.** A hosted worker in each API process periodically marks expired holds. Read/write operations also normalize expired records, so correctness does not depend on a browser or user making an API call. Seat calculations count only unexpired `HELD` records and `CONFIRMED` records.
6. **Seat allocation is serialized by PostgreSQL.** Every hold-creation transaction locks its class row with `SELECT ... FOR UPDATE`, expires old holds, checks active applications and capacity, then inserts the new hold. The lock is database-wide and therefore coordinates multiple API processes sharing this database. A partial unique index additionally enforces one `HELD`/`CONFIRMED` application per student/class. Startup migrations are protected by a PostgreSQL advisory lock so two API processes can start against an empty database safely.
7. **First come, first served means database lock acquisition order.** Under simultaneous network traffic, PostgreSQL serializes requests in the order they acquire the class-row lock. No lottery or random selection is used.
8. **Payment is simulated.** Clicking `ভর্তি ফি দিন` calls the confirm endpoint and is treated as a successful payment. No real payment gateway or payment data is collected.
9. **Cancellation applies to unconfirmed holds.** A confirmed admission cannot be cancelled through the provided endpoint. Repeated cancellation of an already cancelled/expired hold is treated as successful and does not change seat counts.
10. **Class creation is available in the UI without an admin login.** The brief requires an admin screen but explicitly says login is not required. A production system would add role-based authentication and authorization.
11. **No class update/delete API is added.** The supplied API contract defines class creation, listing, and details only. Capacity changes could invalidate existing admissions and are therefore outside this implementation.
12. **Application data is retained in PostgreSQL.** Docker Compose uses a named `postgres_data` volume. `docker compose down` preserves it; `docker compose down -v` intentionally deletes it. Backend tests use a separate `school_admission_test` database and volume.
13. **Errors are returned as JSON.** Validation errors use 400, missing resources use 404, capacity/duplicate/state conflicts use 409, and unexpected server failures use a generic 500 response without exposing internal details.
14. **The bonus uses two real API containers.** `backend` and `backend2` run the same API image on host ports 8080 and 8081 and connect to the same PostgreSQL database. Database row locking, rather than process-local state, enforces the shared capacity limit.
